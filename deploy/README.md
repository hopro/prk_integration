# Система «ИАС-4: работа с прикреплениями»

Комплект для развёртывания на стороне заказчика. Всё запускается через Docker
Compose, внешние сервисы разворачиваются рядом.

## Состав

| Сервис            | Назначение                                                       |
|-------------------|------------------------------------------------------------------|
| `frontend`        | Веб-интерфейс (nginx + React). Доступен из браузера              |
| `backend`         | Сервер приложения: SOAP-запросы в ИАС-4, прокси к шлюзу, SQLite  |
| `gateway`         | Шлюз в ЕЦП: авторизация, сессии, прокси к ЕЦП                    |
| `gateway-postgres`| Учётные записи шлюза (в том числе логин/пароль ЕЦП)              |
| `gateway-redis`   | Сессии ЕЦП шлюза                                                 |

Почему нужен шлюз: ЕЦП не отдаёт данные по простой HTTP-аутентификации — нужна
сессия, которая протухает. Шлюз владеет этой сессией, сам переавторизуется и
переживает её обрыв. Поэтому учётные данные ЕЦП хранятся **в шлюзе**, и именно
он обращается к ЕЦП.

## Требования

- Docker Engine 24+ и Docker Compose v2
- 2 ГБ ОЗУ, 10 ГБ на диске
- Доступ из сети заказчика к его ИАС-4 и ЕЦП
- Открытый порт, указанный в `APP_PORT` (по умолчанию 3001)

## Установка

```bash
cp .env.example .env
nano .env          # обязательно: GATEWAY_DB_PASSWORD, JWT_SECRET_KEY,
                   #             GATEWAY_LOGIN, GATEWAY_PASSWORD
docker compose up -d --build
```

Проверка:

```bash
docker compose ps                                  # все сервисы healthy
curl -fsS http://localhost:8010/health             # шлюз — изнутри сети
open http://<host>:3001
```

### Выгрузки ТФОМС

Справочники СПМО/СМО/подразделений берутся из XML-выгрузок. Положите файлы в
каталог `./tfoms` рядом с `docker-compose.yml`:

```
tfoms/SPSMO.zip  SPSMO.zip  SPDEPT.xml  SPSUBDEPT.xml
```

Дальше они подхватятся автоматически: кнопка «Загрузить» на вкладке
«Справочники» сама найдёт нужный файл. Формат — ZIP с XML в кодировке
windows-1251. Кодировку можно сменить в настройках («Кодировка выгрузок ТФОМС»).

## Первоначальная настройка в интерфейсе

Откройте систему, нажмите **шестерёнку** справа сверху и заполните:

1. **ИАС-4** — логин и пароль, выданные заказчиком для ИАС-4.
2. **ЕЦП** — `ID МО (Lpu_id)`, логин и пароль ЕЦП. Пароль проверяется на ЕЦП
   при сохранении: если ЕЦП его не примет, система скажет об этом сразу и
   ничего не сохранит.
3. **Адреса сервисов** — адрес ЕЦП и адреса ИАС-4 для двух SOAP-операций
   (прикрепление ЗЛ и проверка полиса). Значения из `.env` подставляются при
   первом запуске, дальше их можно менять здесь же.

Учётные данные ЕЦП и его адрес хранятся в шлюзе — он источник правды. Локальная
копия в SQLite нужна только для отображения и восстановления.

### Возможная ошибка: «Нет прав доступа»

Если ЕЦП отвечает `Нет прав доступа`, пароль верен, но у пользователя в ЕЦП нет
группы **«Пользователь API»**. Группу назначает администратор РИШ/ЕЦП — это
вне системы.

## Справочники

Вкладка **«Справочники»**:

| Справочник         | Источник          | Когда нужен                        |
|--------------------|-------------------|------------------------------------|
| Участки ЛПУ        | ЕЦП               | Поиск `LpuRegion_id` при отправке карты |
| Подразделения МО   | SPDEPT.xml        | Выбор кода `podr` в форме прикрепления |
| Мед. организации   | SPMO.zip          | Выбор МО                           |
| Страховые компании | SPSMO.zip         | Выбор СМО                          |


Коды ИАС-4 и участки ЕЦП — разные нумерации, совпадений мало, поэтому связку
проставляет администратор на вкладке «Сопоставление участков». Подробности и
сводка сверки — в `dictionaries/README.md`.

Загрузка выполняется по кнопке «Загрузить», результат хранится локально и
используется при работе с пациентами. Если участки не загружены, система
обращается к ЕЦП напрямую, но это медленнее и создаёт лишнюю нагрузку.

Форматы файлов и примеры — в каталоге `dictionaries/`.

## Обслуживание

```bash
docker compose logs -f backend        # логи сервера
docker compose logs -f gateway        # логи шлюза, в т.ч. работа с ЕЦП
docker compose restart gateway        # шлюз переподключится к ЕЦП сам
docker compose up -d --build          # обновление после замены файлов
```

### Где лежат данные

| Что                       | Где                                   |
|---------------------------|---------------------------------------|
| Настройки и пароли         | `data/settings.db` (том `./data`)     |
| История запросов           | `data/prk_history.db`                 |
| Справочники                | `data/dictionaries.db`                |
| Логин/пароль ЕЦП           | PostgreSQL шлюза (том `gateway_pg`)   |

**Каталог `data` нельзя удалять** — в нём рабочие данные. Резервная копия:

```bash
docker compose stop backend
tar czf backup-$(date +%F).tgz data
docker compose start backend
```

### Диагностика

```bash
# Состояние шлюза и ЕЦП
docker compose exec gateway python -c "print('ok')"
docker compose exec gateway redis-cli --scan --pattern 'mis_session:*'

# Проверка связи с ЕЦП из шлюза
docker compose exec gateway python - <<'PY'
import httpx
r = httpx.get("https://<хост ЕЦП>/api/user/login",
              params={"Login": "<логин>", "Password": "<пароль>"}, timeout=30)
print(r.status_code, r.text[:200])
PY
```

Если в логах шлюза нет строк вида `MIS auth OK for <логин>`, значит до ЕЦП не
дошли — проверьте адрес и учётные данные.

## Приложение A. Переменные окружения

Все переменные перечислены в `.env.example`. Обязательные: `GATEWAY_DB_PASSWORD`,
`JWT_SECRET_KEY`, `GATEWAY_LOGIN`, `GATEWAY_PASSWORD`.

Адреса сервисов (`SOAP_URL`, `SOAP_CHECK_URL`, `MIS_BASE_URL`) — значения по
умолчанию. После первого запуска они записываются в базу и правятся из
интерфейса; чтобы вернуть исходные значения, очистите поля адресов в
шестерёнке и перезапустите backend.

Значения `SOAPAction` протоколом ИАС-4 заданы жёстко
(`http://tfoms.e-burg.ru/srv_loadprk/LoadPrk` и
`http://tempuri.org/GetInsPrkState`), поэтому в настройках их нет.

## Приложение B. Обновление

```bash
# заменить файлы, затем
docker compose up -d --build
```

Данные в `data/` и в томе `gateway_pg` сохраняются. Удалять тома
(`docker compose down -v`) нельзя — это удалит учётные данные ЕЦП и историю.

## Сети и почему шлюз может быть недоступен

Схема разделена на две сети:

| Сеть | Кто в ней | Назначение |
|------|-----------|-----------|
| `prk_app` | frontend, backend, gateway | обмен между компонентами системы |
| `prk_gateway_data` (`internal: true`) | gateway, gateway-postgres, gateway-redis | базы шлюза, без выхода в интернет |

`internal: true` означает, что у Postgres и Redis нет маршрута наружу и они не
видны из `backend` и `frontend` — достучаться до них можно только из шлюза.

Backend обращается к шлюзу по имени сервиса: `MIS_GATEWAY_URL=http://gateway:8010`.
Это работает, пока оба контейнера в одной сети `prk_app`.

### Если backend пишет «Шлюз ЕЦП недоступен»

Быстрая проверка из браузера, без доступа к серверу:

```
http://<адрес>:3001/api/v1/auth/gateway-health
```

Ответ разбирает связь по шагам — `resolve`, `tcp`, `health`, `login` — и в поле
`hint` пишет, что именно чинить:

Поля в ответе:

| Поле | Значение |
|------|----------|
| `verdict` | итог одной строкой |
| `peer` | адрес, на который соединение приземлилось **на самом деле** |
| `steps.tcp.addresses` | во сколько адресов разрешилось имя, кто из них ответил |
| `service` | кто ответил: `mis-gateway` или `prk-backend` |

Типовые вердикты:

| `verdict` | Что означает | Что делать |
|-----------|--------------|------------|
| `шлюз доступен, вход работает` | всё в порядке | — |
| `MIS_GATEWAY_URL указывает на сам backend` | адрес шлюза содержит адрес самого backend | уберите `MIS_GATEWAY_URL` из `.env` |
| `по этому адресу не наш шлюз` | по адресу слушает другая программа | укажите адрес своего шлюза |
| `шлюз есть, вход не удался` | шлюз отвечает, но логин или пароль неверны | проверьте `GATEWAY_LOGIN`/`GATEWAY_PASSWORD` |

Смотреть `docker logs` не обязательно: при старте backend сам пишет вердикт
одной строкой:

```
МИС-ШЛЮЗ настроен на http://gateway:8010
МИС-ШЛЮЗ: url=http://gateway:8010 пир=172.20.0.4:8010 сервис=mis-gateway вход=422 наш_шлюз=True
МИС-ШЛЮЗ готов: адрес=http://gateway:8010 пир=172.20.0.4:8010 сервис=mis-gateway
```
| `tcp` | имя разрешилось, порт 8010 не принимает | `docker compose logs gateway`; шлюз должен слушать `0.0.0.0:8010` |
| `health` | шлюз не отвечает на `/health` | смотрите логи шлюза |
| `login` | шлюз отвечает, но вход не удался | не заданы `GATEWAY_LOGIN` / `GATEWAY_PASSWORD` в `.env` |

### По адресу отвечает не наш шлюз

Признак в логах backend:

```
RuntimeError: Шлюз ЕЦП по адресу http://… отклонил вход: 404 {"detail":"Not Found"}
```

`404 {"detail":"Not Found"}` — это ответ программы, у которой нет маршрута входа.
Наш шлюз на `POST /api/v1/auth/login` отвечает `422` (пустое тело запроса) или
`401` (неверные учётные данные), но никогда не `404`.

Чаще всего это **сам backend**: у него `/api/health`, но нет
`/api/v1/auth/login`. Случается, когда в `.env` попадает адрес самого backend —
например, `MIS_GATEWAY_URL=http://localhost:8000`.

Проверьте:

```bash
grep MIS_GATEWAY_URL .env
```

Правильно — **не задавать его вовсе**: compose подставит `http://gateway:8010`,
то есть шлюз из этого же compose. Если шлюз развёрнут отдельно — укажите его
адрес явно. Адрес машины, на которой compose запускали в последний раз, в `.env`
попадать не должен.

Всё это показывает `GET /api/v1/auth/gateway-health` в поле `verdict`
и `hint`, с указанием адреса, на который соединение приземлилось на самом деле.

### Смена пароля базы шлюза

Пароль Postgres задаётся только при первом запуске: он записывается в том
`gateway_pg`. Если изменить `GATEWAY_DB_PASSWORD` в `.env` и не трогать том,
шлюз перестанет подниматься с

```
password authentication failed for user "mis_gateway"
```

Пароль в томе надо менять так:

```bash
docker compose exec gateway-postgres psql -U mis_gateway -d mis_gateway \
  -c "ALTER USER mis_gateway WITH PASSWORD 'новый_пароль';"
```

Либо снести том и начать с нуля — тогда пропадёт учётная запись администратора,
её придётся создавать заново.

Частая причина, когда Docker Desktop или хост внутри домена: поисковые домены
хоста наследуются контейнерами, и имя несуществующего сервиса уходит во внешний
DNS, разрешается во внешний адрес, и соединение виснет. В таком случае укажите в
`.env` для backend `MIS_GATEWAY_URL` с IP-адресом контейнера шлюза, а не его имя.

Профилактика уже встроена: `backend` ждёт `gateway` в состоянии `healthy`
(`depends_on: condition: service_healthy`), а вход в шлюз повторяется 6 раз с
паузой 2 секунды — если шлюз ещё поднимается, ошибки не будет.

nginx тоже не падает при перезапуске backend: имя `backend` разрешается на
каждый запрос (`resolver 127.0.0.11`), а не один раз при старте.
