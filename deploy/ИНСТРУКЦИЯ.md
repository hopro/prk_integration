# Развёртывание и обновление

Инструкция для администратора организации. Предполагается умение открыть
терминал на сервере и выполнять команды из этого файла.

Что нужно на сервере: Docker и Docker Compose. Проверка:

```bash
docker version && docker compose version
```

Всё остальное ставится само при первом запуске.

---

## 1. Установка с нуля

### Шаг 1. Получить код

```bash
git clone <адрес-репозитория> prk_integration
cd prk_integration
```

### Шаг 2. Положить справочники

Справочники — это файлы выгрузок. Положите их в каталог `tfoms`:

```bash
mkdir -p tfoms
cp /путь/к/вашим/файлам/SPSMO.zip tfoms/
cp /путь/к/вашим/файлам/SPMO.zip tfoms/
cp /путь/к/вашим/файлам/SPDEPT.xml tfoms/
cp /путь/к/вашим/файлам/SPSUBDEPT.xml tfoms/
```

| Файл | Что это | Обязателен |
|------|---------|-----------|
| `SPDEPT.xml` | подразделения ИАС-4: коды `PODR`, которые ИАС-4 принимает как подразделение | **да** |
| `SPSUBDEPT.xml` | ФАПы, медкабинеты, дневные стационары — те же коды в `PODR` | желательно |
| `SPMO.zip` | медицинские организации | нет, но нужен для выбора МО |
| `SPSMO.zip` | страховые компании | нет, но нужна для выбора СМО |

`SPDEPT.xml` допускает `.zip` и `.csv` вместо `.xml`. Пример формата —
`dictionaries/SPDEPT.example.xml`.

Без `SPDEPT.xml` система запустится, но форма прикрепления не сможет предложить
список подразделений и сообщит об этом.

### Шаг 3. Создать `.env`

```bash
cp .env.example .env
```

Откройте `.env` и задайте **четыре** значения:

```
GATEWAY_DB_PASSWORD=пароль_базы_данных
JWT_SECRET_KEY=длинная_случайная_строка
GATEWAY_LOGIN=admin
GATEWAY_PASSWORD=пароль_администратора
```

Подойдёт любой набор букв и цифр. Сгенерировать можно так:

```bash
openssl rand -base64 24
```

Остальные строки в `.env` — рабочие умолчания, менять их не нужно.

> **`GATEWAY_DB_PASSWORD` задаётся только при первом запуске.** Пароль
> сохраняется в томе Postgres. Если поменять его в `.env` позже, шлюз перестанет
> подниматься с `password authentication failed for user "mis_gateway"`. Как
> поменять правильно — в разделе 5.

> **`MIS_GATEWAY_URL` в `.env` не нужен.** Compose сам подставит
> `http://gateway:8010`, то есть шлюз из этого же развёртывания. Задавайте его
> только если шлюз развёрнут отдельно.

### Шаг 4. Запустить

```bash
docker compose up -d --build
```

Первый запуск занимает несколько минут: собираются образы и создаётся база.

### Шаг 5. Проверить

Откройте в браузере:

```
http://<адрес-сервера>:3001/api/v1/auth/gateway-health
```

Поле `verdict` должно быть:

```json
"verdict": "шлюз доступен, вход работает"
```

Если поле другое — смотрите раздел 4 «Если что-то не работает».

Затем откройте саму систему `http://<адрес-сервера>:3001` и настройте учётные
данные ЕЦП: шестерёнка в шапке → «Учётные данные ЕЦП».

### Шаг 6. Загрузить справочники

Вкладка «Справочники»:

- **Подразделения МО (справочник ИАС-4)** и **ФАПы (SPSUBDEPT)** →
  «Обновить из XML»;
- **Медицинские организации**, **Страховые компании** → «Обновить из XML»;
- **Участки ЛПУ** → «Обновить из ЕЦП», Лpu_id берётся из настроек.

### Шаг 7. Сопоставить подразделения ИАС-4 с участками ЕЦП

Обязательный шаг: без него прикрепление не будет знать, в какой участок ЕЦП
сохранять карту пациента.

Вкладка **«Сопоставление участков»**:

1. Нажмите **«Подобрать автоматически»**, затем **«Применить»**. Так свяжутся
   и коды, совпавшие с названием участка, и ФАПы — их находит сравнение названий
   с описанием участка. Для ГП № 4 так связываются 82 подразделения из 114.
2. Остальное привяжите вручную: в выпадающем списке выберите участок ЕЦП для
   нужного кода. Участок показан как `LpuRegion_Name` и `LpuRegion_Descr`.
3. Дождитесь, чтобы счётчик **«Не привязано»** стал нулём.

Подразделения, у которых в выгрузке снят признак «разрешено прикрепление»
(`PRKYES = 0`), по умолчанию скрыты — ИАС-4 такие отклоняет с кодом 502.
Показать их можно галочкой «показать запрещённые»: их видно, но связывать
смысла нет, кроме как отметить «отвязано вручную».

Закрытые по сроку действия подразделения видны всегда и помечены в таблице:
в форму выбора прикрепления они не попадают.

Участки, которые в ИАС-4 использовать не нужно, отвяжите кнопкой со значком
разрыва: автоподбор больше не будет их предлагать. Кнопка рядом возвращает код
в автоматический подбор.

Сколько участков занято, видно по счётчикам вверху страницы. Значение
«Битых привязок» больше нуля означает, что привязанный участок исчез из ЕЦП —
обновите участки из ЕЦП и привяжите заново.

## 2. Обновление до новой версии

Две команды. Настройки и данные сохраняются: `.env`, каталог `${DATA_DIR}` и
тома баз данных не входят в git, поэтому `git pull` их не трогает.

```bash
cd prk_integration
git pull
docker compose up -d --build
```

Что происходит:

- `git pull` забирает новый код;
- `docker compose up -d --build` пересобирает образы и пересоздаёт контейнеры с
  новым кодом, перезапуская те, чья конфигурация не изменилась;
- база Postgres обновляется сама при старте шлюза (миграции Alembic), данные не
  теряются.

Проверка после обновления — та же, что при установке:

```
http://<адрес-сервера>:3001/api/v1/auth/gateway-health
```

Посмотреть, что изменилось, — файл `CHANGELOG.md` в корне репозитория.

> **Первый запуск после обновления занимает дольше обычного:** сборка образов
> заново. Это нормально.

> **Если `docker compose up` завершился ошибкой — повторите ту же команду.**
> Containerы, которые не смогли стартовать, остаются в старой конфигурации, и
> вторая попытка их пересоздаёт. Проверено: первая попытка может вернуть ошибку,
> вторая поднимает систему. Ничего удалять при этом не нужно.

```bash
docker compose up -d --build        # если первая попытка дала ошибку — просто повторите
```

Данные при этом не теряются: `.env`, каталог `${DATA_DIR}` и тома баз не входят в
git и не пересоздаются командой `up`.

### Откат на предыдущую версию

```bash
cd prk_integration
git log --oneline -5          # найти нужный коммит
git checkout <коммит>
docker compose up -d --build
```

Вернуться обратно: `git checkout main`.

Откат не отменяет миграции базы данных, поэтому откатывайтесь только на версии,
с которой система работала. Данные в SQLite не трогаются при откате.

## 3. Что где хранится

| Что | Где | Терять нельзя |
|-----|-----|---------------|
| Настройки, пароли ИАС-4, адреса сервисов | `${DATA_DIR}/settings.db` | да |
| Справочники | `${DATA_DIR}/dictionaries.db` | нет, загружаются заново |
| История прикреплений | `${DATA_DIR}/prk_history.db` | да |
| Учётные данные ЕЦП, сессии | том `gateway_pg` | да |
| Справочники ТФОМС | `./tfoms/*.zip`, `./tfoms/*.xml` | нет, загружаются заново |

Резервная копия всего состояния:

```bash
tar czf backup-$(date +%F).tar.gz .env data/
docker compose exec -T gateway-postgres pg_dump -U mis_gateway mis_gateway > backup-db-$(date +%F).sql
```

Восстановление: положить `.tar.gz` на место, распаковать в каталог,
`docker compose up -d`.

## 4. Если что-то не работает

### Первым делом посмотрите вердикт

```
http://<адрес-сервера>:3001/api/v1/auth/gateway-health
```

Поле `verdict` называет проблему:

| `verdict` | Что делать |
|-----------|-----------|
| `шлюз доступен, вход работает` | всё в порядке |
| `MIS_GATEWAY_URL указывает на сам backend` | в `.env` попал адрес самого backend. Удалите строку `MIS_GATEWAY_URL` |
| `по этому адресу не наш шлюз` | в `.env` указан не адрес шлюза. Удалите строку, если шлюз из этого же compose |
| `шлюз есть, вход не удался` | неверны `GATEWAY_LOGIN` или `GATEWAY_PASSWORD` в `.env` |

### Логи

```bash
docker compose logs -f            # всё сразу
docker compose logs -f backend    # сервер приложения
docker compose logs -f gateway    # шлюз в ЕЦП
docker compose ps                 # состояние контейнеров
```

При старте backend пишет в лог вердикт по шлюзу. Ищите строку `МИС-ШЛЮЗ`:

```
МИС-ШЛЮЗ настроен на http://gateway:8010
МИС-ШЛЮЗ: url=http://gateway:8010 пир=172.20.0.4:8010 сервис=mis-gateway вход=422 наш_шлюз=True
МИС-ШЛЮЗ готов
```

### Контейнеры не стартуют

`docker compose ps` покажет exited или restarting. Смотрите лог этого сервиса.
Частые причины:

- **`password authentication failed for user "mis_gateway"`** — в `.env` изменён
  `GATEWAY_DB_PASSWORD`, а в базе остался прежний. См. раздел 5.
- **Ошибка про незаполненный `.env`** — не задано одно из четырёх обязательных
  значений.
- **Занят порт** — порт из `APP_PORT` в `.env` уже занят другим приложением.
  Смените `APP_PORT`.

### Не открывается интерфейс

```bash
docker compose ps
curl -s http://127.0.0.1:3001/api/health
```

Если `curl` отвечает, а браузер нет — проверьте, открыт ли порт в сетевом экране
сервера и не включено ли `APP_PORT` не на том интерфейсе.

### Справочники не загружаются

- Вкладка «Справочники» показывает, что не загружено;
- «Обновить из XML» читает файл из `./tfoms`. Если его там нет — положите;
- «Подразделения МО (ИАС-4)» загружается только кнопкой «Загрузить файл»;
- участки ЛПУ загружаются только из ЕЦП, файлом они не загружаются.

### Подразделение ИАС-4 не привязано к участку ЕЦП

В истории прикреплений или в ответе ИАС-4 будет сообщение, что участок не найден.
Значит, код подразделения не сопоставлен с участком ЕЦП.

Откройте вкладку «Сопоставление участков», найдите код в поиске и выберите ему
участок. Быстрее всего — кнопка «Подобрать автоматически», но участки, названные
текстом с суффиксом `_ГРП`, автоматика не распознаёт: их нужно привязать руками.

### Ошибка «участок не найден в ЕЦП»

Привязка сохранена, но участка с таким кодом больше нет в списке ЕЦП — обычно
после того, как участок в ЕЦП переименовали или закрыли.

Обновите участки из ЕЦП на вкладке «Справочники», затем привяжите код заново.
Счётчик «Битых привязок» на странице сопоставления покажет все такие случаи.

### Обновление прошло не полностью

Если `docker compose up -d --build` вернул ошибку, проверьте состояние:

```bash
docker compose ps
```

Контейнер в статусе `unhealthy` или `restarting` означает, что он не смог стартовать
и остался в прежней конфигурации. Повторите ту же команду — контейнер будет
пересоздан:

```bash
docker compose up -d --build
```

Если повторение не помогло:

```bash
docker compose down          # контейнеры и сети, но НЕ тома и не данные
docker compose up -d --build
```

`docker compose down` без `-v` не трогает тома баз данных и каталог `${DATA_DIR}`,
поэтому настройки, справочники, история и учётная запись администратора сохраняются.

### Обновление упало с «port is already allocated»

Значит, кроме контейнеров этого развёртывания порт держит что-то ещё. Чаще всего
это контейнеры прежней версии: они остаются жить, пока их не снимут. Найдите, кто
держит порт:

```bash
docker ps --format "{{.Names}}\t{{.Ports}}" | grep 3001
```

Если это контейнеры старой установки, снимите их и повторите обновление:

```bash
docker compose down --remove-orphans
docker compose up -d --build
```

## 5. Смена пароля базы данных шлюза

Пароль задаётся при первом запуске и хранится в томе. Чтобы сменить его на
рабочей системе, менять нужно и в `.env`, и в самой базе:

```bash
# 1. Новый пароль в .env, затем:
docker compose up -d gateway-postgres

# 2. Тот же пароль в базе:
docker compose exec gateway-postgres psql -U mis_gateway -d mis_gateway \
  -c "ALTER USER mis_gateway WITH PASSWORD 'новый_пароль';"

# 3. Перезапуск шлюза:
docker compose up -d gateway
```

Если нужен полный сброс с потерей учётной записи администратора:

```bash
docker compose down -v      # -v удаляет том с базой
docker compose up -d
```

## 6. Перенос на другой сервер

```bash
# На старом сервере
tar czf prk-state.tar.gz .env data/
docker compose exec -T gateway-postgres pg_dump -U mis_gateway mis_gateway > prk-db.sql

# На новом сервере
git clone <адрес-репозитория> prk_integration
cd prk_integration
cp /путь/к/prk-state.tar.gz .
tar xzf prk-state.tar.gz
docker compose up -d gateway-postgres
docker compose exec -T gateway-postgres psql -U mis_gateway -d mis_gateway < prk-db.sql
docker compose up -d --build
```

Сертификат TLS для адресов ИАС-4 и ЕЦП на новом сервере нужно выпустить заново
у вашего администратора.

## 7. Миграция со старой версии

Относится только к системам, развёрнутым до версии 1.1.0. Признак: в `.env`
есть `MIS_GATEWAY_URL` с адресом вида `http://10.0.100.5:8010` или
`http://localhost:8010`, а `docker compose ps` показывает контейнеры, работающие
в режиме `network_mode: host`.

### Шаг 1. Убрать адрес шлюза из `.env`

```bash
sed -i '/^MIS_GATEWAY_URL=/d' .env
```

Compose подставит `http://gateway:8010` — адрес шлюза из этого же развёртывания.

### Шаг 2. Снять старые контейнеры

Старая версия держала контейнеры в режиме `network_mode: host`, поэтому они
продолжают занимать порты и после обновления мешают новым.

```bash
docker compose down --remove-orphans
docker ps -a --filter "name=<имя-проекта>"     # посмотреть, что осталось
```

Если контейнеры со старым именем проекта всё ещё числятся:

```bash
docker rm -f <имя-проекта>-backend-1 <имя-проекта>-frontend-1
```

### Шаг 3. Обновиться как обычно

```bash
git pull
docker compose up -d --build
```

Данные в `${DATA_DIR}` и тома баз сохранятся. Справочники придётся загрузить
заново: в старой версии они лежали в другой базе. Вкладка «Справочники» →
«Обновить из XML», для подразделений ИАС-4 → «Загрузить файл».
